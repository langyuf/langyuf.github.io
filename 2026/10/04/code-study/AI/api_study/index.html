二、理解消息的API格式

消息格式使我们能够将以对话形式提出的请求结构化为对 Claude 的调用，从而保持对话的上下文完整性。这种消息格式能够保留整个对话的历史记录，包括用户和助手发送的所有消息。这样，当 Claude 生成回复时，它能够获取到完整的对话上下文信息，从而得出更加连贯且相关的回答。

检查消息的响应情况

除了 content 之外， Message 对象还包含一些其他的信息：
  id – 一个唯一的对象标识符
  type - 对象类型，始终为“消息”
  role – 生成的消息在对话中的角色。无论何时，它都将是“助手”的角色。
  model - 负责处理请求并生成响应的模型
  stop_reason – 这是模型停止生成数据的原因。我们稍后会进一步了解这个问题。
  stop_sequence – 我们稍后会详细了解这一点。
  usage – 关于计费和使用限定的信息。包含以下内容：

  •   input_tokens – 所使用的输入标记的数量。
  •   output_tokens - The number of output tokens that were used.
  •   soutput_tokens – 实际使用的输出标记数量。

Exercise ：Few-Shot

  • Zero-shot（0-shot）：不给范例、直接问。
  • One-shot（1-shot）：先给 1 个“输入 → 答案”范例再问。
  • Few-shot（下面用的 3-shot 就是）：给几个（通常 2-5 个）范例再问——LLM 照着范例的格式跟判断标准做，准确率通常明显变高。

三、Tool use

agent范式

范式 是什么 在哪学
CoT（Chain-of-Thought、思维链） LLM 写出推理过程再给答案、不只给结论——是个 prompting 技巧、不是 agent 结构 Stage 2 学习目标 + 动手练习（推理任务 CoT）
ReAct（Reasoning + Acting） 在 Loop 里套 CoT：Thought（想）→ Action（调用 tool）→ Observation（看结果）→ Thought …，是 Loop 部件最常见的实现 本 stage 练习 3 + ReAct paper (Yao 2022)
Reflection 跑完一轮后让 LLM 批改自己、根据 feedback 重答 本 stage 反思（concept + 路由）
Planning（任务分解） 把大任务拆成子任务、可分给多个 agent 各做 Stage 4 什么是 multi-agent framework

先懂风险：给 agent 工具 = 给它一个攻击面

把工具交给 LLM 的那一刻，你也给了它一个攻击面。最清楚的框架是 Simon Willison 的 lethal trifecta（致命三角）：当一个 agent 同时具备这三件事，就可能被攻击者操控去偷数据再外传——

  1. 能访问私密数据（你的文件 / DB / API key）
  2. 会接触不可信内容（网页、Email、别人传的文档，里面可能藏指令）
  3. 能对外发送东西（发 request、寄信、写文件）

根因是 LLM 会“照内容里的指令做”，分不清哪些是你下的、哪些是不可信数据里夹带的——这就是 prompt injection。

智能体调用工具的三种方式概述

  • 函数调用方式：各语言模型需自行编写方法调用外部工具，如OpenAI和DeepSeek需分别实现调用逻辑，存在重复开发问题

  • MCP协议：通过统一服务端提供工具集，不同语言模型均可调用，避免重复造轮子

    主要缺陷：

    • 上下文爆炸：返回全部工具会占用大量上下文窗口
    • 选择困难：智能体无法自主判断适用工具，需反复咨询语言大模型
    • 效率问题：组合工具使用时需多次交互，造成Token浪费

  • Agent Skills：赋予智能体专业知识能力，使其自主选择最优工具组合（第三种方式）

    核心思想：

    ​ 通过领域专业化（如农业专家角色）使智能体具备：

    • 工具选择能力：识别单工具适用性
    • 组合优化能力：判断多工具协同方案

    优势：仅需加载必要工具，避免MCP协议的全量返回问题

    \1. 渐进式加载（元数据→工具文档→辅助脚本）

    \2. 领域知识预载（如农业专家角色）

    \3. 动态工具选择（按需调用，减少冗余）

    • 加载机制：
      • 启动阶段：加载领域知识元数据（工具索引、专业能力框架）
      • 特点：不包含具体工具文档/脚本，仅建立知识关联
    • 元数据内容：
      • 领域专业知识库
      • 工具目录索引
      • 工具组合策略知识

结构化输出（Structured Outputs / JSON mode）

Function Calling 是让模型选择“做什么动作”；Structured Output 是让模型保证“输出什么格式”。

要自动执行 → Function Calling

工具多 → 重点优化 description

要稳定解析 → Structured Outputs 我要模型严格按照某个 JSON 格式回答

参数多 → 使用 JSON Schema Structured Outputs 的一种

三种做法（由弱到强）：

  1. prompt 要求 JSON——最简单、但模型有时会多嘴或格式跑掉。
  2. JSON mode / response_format——API 保证返回合法 JSON（但不保证符合你的 schema）。
  3. JSON-schema 强制 / constrained decoding——连 schema 都锁死，返回的一定符合（最可靠）。
